## 1. 一次请求发生了什么

```
用户输入
  │
  ├─► 限流（device 级，内存滑动窗口）
  │
  ├─► 安全分级  safety.classify(text, 最近几轮的 level)
  │     ├─ L3 危机/医疗/法律/未成年 ──► 直接返回写死的模板，结束
  │     ├─ 越界诱导 ─────────────────► 直接返回拒绝模板，结束
  │     └─ L0/L1/L2 ──┐
  │                   ▼
  ├─► 编译 system prompt（人格 × 本轮幽默系数 × 最近用过的句式）
  │
  ├─► 模型生成（一次拿全文）
  │
  ├─► 质量闸门：句数/字数/emoji/Markdown/禁用词
  │     ├─ 不合格 ──► 带原因重写一次 ──► 仍不合格 ──► 保留首尾截断
  │     └─ 合格
  │
  ├─► 落库（消息 + 梗指纹）
  │
  └─► 按字符回放成 SSE ──► 前端打字机
```

## 2. 五个关键决策与取舍

### 2.1 L3 不交给模型

**决策**：危机、医疗、法律、未成年四类，回复是写死的模板，只做变量替换。

**为什么**：把最不能出错的一步，交给最不可控的组件，是设计错误。
模型可能被诱导、可能幻觉、可能"安慰式"地淡化危机。

**代价**：读起来像模板，缺少温度。

**为什么接受**：在危机场景，"不像人"是可接受的缺陷，"说错话"不是。

### 2.2 先拿全文，再回放成流

**决策**：`provider.complete()` 返回完整文本，校验通过后用 2 字符/12ms 的节奏
推成 SSE。不是真流式。

**为什么**：长度与合规校验必须在用户看到之前完成。
真流式意味着不良内容会先流出去，再撤回——撤不回。

**代价**：首字延迟多了一次完整生成的时间。

**什么时候该改**：回复长度稳定在 200 字以上时，缓冲的收益会被延迟吃掉，
那时应该改成"句子级缓冲"（按标点切块，逐句校验逐句放行）。

### 2.3 内置 mock provider

**决策**：`OAD_PROVIDER=mock` 是默认值，不联网、不要 key。

**为什么**：开源项目的第一道门槛是"能不能在 3 分钟内跑起来"。
如果必须先申请 API key，90% 的人会在这里流失。

**代价**：mock 的输出是模板拼装，多聊几轮会看出重复。

**它真正的用途**：作为评测的下限基线。任何真实模型都应该明显好于它，
否则说明接入或 prompt 有问题。

### 2.4 SQLite + 裸 sqlite3

**决策**：不上 ORM，不上 Postgres（作为可选项保留）。

**为什么**：四张表，贡献者读 80 行 SQL 比读 ORM 配置快。
`docker compose up` 一条命令起得来，不给新手设门槛。

**什么时候该换**：多实例部署、或需要跨设备同步会话时。
`db.py` 的所有函数都是纯 SQL，替换成本可控。

### 2.5 人格包与引擎解耦

**决策**：人格是 YAML 数据，不是代码；引擎只负责解释它。

**为什么**：这样社区能贡献"鲁迅体""新闻联播体"，而不需要改 Python。
更重要的是——**IP 风险被隔离在一个可下线的目录里**。

**代价**：人格表达力受 schema 限制。

**缓解**：`few_shots` 和 `devices.examples` 提供了自然语言的逃生舱。

## 3. 数据模型

```sql
sessions     (id, device_id, persona_id, created_at, updated_at)
messages     (id, session_id, role, content, level, persona_id, meta, created_at)
used_bits    (session_id, bit, created_at)          -- 梗指纹，24h 内不复用
feedback     (message_id, kind, created_at)         -- ◎像 / ○不像
```

`used_bits` 的实现细节：把每条回复的**每句前 6 个字**当作"梗指纹"存下来，
下一轮注入 prompt：「这些句式最近用过了」。

它不是精确的梗识别，而是防"起手式重复"——重复的句式比重复的梗更容易暴露模板感。

## 4. 扩展点

| 想做的事 | 改哪里 | 注意 |
| --- | --- | --- |
| 加一个人格 | `packages/persona/<id>/` | 见 `docs/persona-spec.md` |
| 换模型 | `.env` 里的 `OAD_PROVIDER` | 三者接口一致，实现 `complete()` 即可 |
| 加一个安全规则 | `services/api/app/safety/rules.py` | 改完必须跑金标，漏判必须仍为 0 |
| 加一个幽默装置 | `persona.yaml` 的 `devices` | 必须有 pattern 和 avoid |
| 换存储 | `services/api/app/db.py` | 函数签名保持不变 |
| 做分享卡 | 新增 `apps/web/app/share/` | 不要在分享内容里带用户原文 |

## 5. 没做的部分（诚实清单）

| 项 | 状态 | 原因 |
| --- | --- | --- |
| 分享卡 | 未实现 | 方案 W3 可砍项；涉及用户隐私外带，需要独立设计 |
| 用户登录 | 未实现 | 匿名 device_id 足够验证产品假设 |
| 多实例部署 | 未支持 | 限流是内存态；换成 Redis 才能多实例 |
| 真流式 | 未实现 | 见 2.2，是刻意的取舍 |
| 情感分类模型 | 未接入 | 当前纯规则；接小分类器能提升召回，但会引入模型依赖 |
| 向量记忆 | 未实现 | 无长期记忆；每轮只看最近 8 轮 |

## 6. 一个容易踩的部署坑：`API_ORIGIN` 是构建期变量

前端只请求同源 `/api/*`，由 Next 的 `rewrites` 反代到 FastAPI，好处是没有 CORS、也没有硬编码地址。

代价是：**`rewrites` 会在 `next build` 阶段被写进 `.next/routes-manifest.json`**。因此 `next start` 时再改 `API_ORIGIN` 是无效的，请求仍然发往构建时的地址。

实际表现（作者踩过）：本地 `next build` 时用的是默认 `http://127.0.0.1:8000`，后来把后端起在 8010，用 `API_ORIGIN=http://127.0.0.1:8010 next start` 启动，浏览器访问 `/api/health` 一律 500，后端日志里能看到 `Failed to proxy http://127.0.0.1:8000/api/health ECONNREFUSED`。

对应处理：

| 场景 | 做法 |
| --- | --- |
| `next dev` | 直接读 `next.config.mjs`，`API_ORIGIN` 运行时生效 |
| `next start` | 必须构建时就带上：`API_ORIGIN=... npm run build` |
| Docker | 已用 `ARG API_ORIGIN` + `docker-compose` 的 `build.args` 传入 `http://api:8000` |

如果将来希望运行时可配，需要把反代从 `rewrites` 改成自建 route handler（`app/api/[...path]/route.ts` 里转发），代价是要自己处理流式响应透传。
